# Implementation Plan — Phase 1: Authentication

Status: shipped (2026-09-25)
Date: 2026-09-25
Parent plan: `plan/2026-09-25-mvp-initial-plan.md`

## Objective

Users can sign up and sign in with email/password (email verification required) or Google. Each user has one role: `student`, `msme` or `admin`. Students and MSMEs pick their role; admins are created by a seed script. Pages are protected by role on the server.

## Current State

Phase 0 foundation: Next.js 16.3.6, Prisma 7.10.0 with no models, pino → Loki logging, Mailpit running in Docker Compose. No auth.

## Decisions (user, 2026-09-25)

1. Google sign-in has no role field. A signed-in user without a role is sent to a one-time "choose student or MSME" screen and is blocked from every other protected page until they choose.
2. A role is fixed once set. Only an admin can change it (admin tooling arrives later; in Phase 1 nobody can change a set role through the app).
3. Users cannot sign in until their email is verified. They can resend the verification email.

## Verified Library Facts (checked 2026-09-25)

- `better-auth` 1.7.6 peers: `prisma`/`@prisma/client` `^5 || ^6 || ^7`, `next` `^14 || ^15 || ^16`. Prisma adapter is exported from `better-auth/adapters/prisma`. Schema generator CLI is the `auth` package (1.7.6).
- `user.additionalFields` with `input: false` makes a field server-owned: sign-up/update API input and OAuth profile mapping cannot set it.
- `emailAndPassword.requireEmailVerification` blocks sign-in for unverified users (403) and, with `emailVerification.sendOnSignIn`, re-sends the email on each attempt. With it enabled, sign-up with an existing email returns a generic response instead of an error (no account enumeration).
- The docs advise not awaiting the email send inside `sendVerificationEmail` (timing attacks).
- Next.js 16: `middleware.ts` is renamed `proxy.ts` (inside `src/` here), Node.js runtime only. Better Auth recommends only an optimistic cookie check there (`getSessionCookie`) and real checks in each page/action.
- `nextCookies()` plugin (last in the plugin list) lets server actions set auth cookies.
- `better-auth/crypto` exports `hashPassword` (used by the seed).
- Prisma 7 config supports `migrations.seed`.

## Design

- **Role storage:** `User.role` is a nullable Prisma enum `Role`. `null` means "role not chosen yet". Declared to Better Auth as an `additionalField` with `input: false`, so clients can never write it.
- **Setting a role:** only application code writes it, through one function `assignInitialRole(userId, role)` which (a) accepts only `student` or `msme` (zod), and (b) runs `updateMany where { id, role: null }`, so an existing role can never be overwritten. Used by the sign-up server action and the choose-role server action.
- **Email sign-up:** a server action validates name/email/password/role, calls `auth.api.signUpEmail`, then `assignInitialRole`. If role assignment fails, the user just sees the choose-role screen after verifying — same path as Google.
- **Sign-in:** client-side `authClient.signIn.email` / `authClient.signIn.social({ provider: "google" })`. A 403 shows "verify your email" with a resend button.
- **Google:** enabled only when both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set (blocker B-003).
- **Routing:** `/dashboard` resolves the home for the current user (no role → `/onboarding/role`, else `/student`, `/msme`, `/admin`). Helpers in `src/lib/authz.ts`: `getSession`, `requireSession`, `requireRole(...roles)`. Wrong role → redirect to `/dashboard`.
- **Proxy:** `src/proxy.ts` redirects to `/sign-in` when no session cookie exists on protected paths. Not a security boundary.
- **Admin seed:** `prisma/seed.ts` creates a verified admin with a credential account from `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Idempotent; refuses to promote an existing non-admin user.
- **Logging:** sign-up, role assignment, verification email sent/failed, seed. Log user IDs, never emails, passwords or tokens.

## Implementation Sequence

1. Install `better-auth@1.7.6`, `nodemailer`, `@types/nodemailer`, `tsx`.
2. Env: `BETTER_AUTH_SECRET` (≥32 chars), `BETTER_AUTH_URL`, `SMTP_HOST`, `SMTP_PORT`, `EMAIL_FROM`, optional Google pair (both or neither). Update `.env.example` and the local `.env`.
3. Schema: generate Better Auth models with `auth@1.7.6 generate`, add `Role` enum, migrate (`init_auth`).
4. `email.ts`, `roles.ts`, `auth.ts`, API route, `auth-client.ts`, `authz.ts`, `proxy.ts`.
5. Pages and server actions.
6. Seed script and `db:seed`.
7. Tests, then lint/typecheck/build.

## Test Strategy

- Unit: `roles.ts` (sign-up role schema rejects `admin`/unknown; home path per role), env validation for new vars.
- Integration (Docker Postgres): `assignInitialRole` sets a null role, refuses to overwrite, refuses `admin`; `auth.api.signUpEmail` with a `role` in the body does not set the role; unverified user sign-in is rejected.
- E2E (Playwright + Mailpit API): sign up as student → verification email arrives → open link → lands on `/student`; `/msme` and `/admin` redirect away; signed-out `/student` redirects to `/sign-in`; unverified sign-in shows the verify message.
- Not testable yet: Google sign-in (no credentials).

## Risks

- Library integration drift (Better Auth + Prisma 7 + Next 16): mitigated by the checks above and real end-to-end tests.
- Role escalation: mitigated by `input: false` plus the single guarded write path, both covered by tests.
- Tests creating users: use unique emails and clean up the rows they create.

## Outcome (2026-09-25)

Deviations from the plan:
- No separate `/verify-email` page. Sign-up shows a "check your inbox" state with a resend button; a blocked sign-in shows a "not verified, new link sent" message (Better Auth re-sends on sign-in).
- The Better Auth CLI needs an exported `auth` instance, while `src/lib/auth.ts` builds one lazily with `getAuth()`. So the schema was generated from a temporary config into a temp file and merged by hand, with `role` changed from `String?` to the `Role` enum.
- Better Auth does more than ignore a `role` in the sign-up body: it rejects the request with 400 ("role is not allowed to be set"). The test asserts that.
- Added an end-to-end test for the choose-role screen, simulated by clearing a new user's role, because Google can't be exercised yet.
- E2E cleanup runs in Playwright `globalTeardown`, not per-worker `afterAll`, so parallel workers can't delete each other's users.
